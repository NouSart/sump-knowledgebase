# 04｜模型、工具与异步任务：回答是怎样真正做出来的

本篇对应 **2026-10-26 的源码快照 `149451db`**。文中源码链接固定到这次提交，今后的版本可能不同。

本次工作是阅读源码与已有测试，**没有在本篇编写过程中执行测试**。下方运行命令是给读者的可选练习，不代表已经通过。

## 1. 读完要会什么

- 分清“模型提出工具请求”和“工具真的执行了”。
- 分清会话、任务、一次网络请求和一项异步工作。
- 看懂为什么先收到“已受理”，稍后才有最终结果。
- 理解一个会话怎样同时管理多个工具，又避免结果串到另一项任务。

先想象你在餐厅点餐。服务员接单，不代表厨师已经做完；两道菜可以分别制作，但每道菜仍须送到正确的桌子。这个比喻只帮助理解状态，实际系统用编号与代码管理，不能凭先后顺序猜归属。

## 2. LLM 不是在聊天框里直接执行程序

**LLM** 是大型语言模型。它能根据输入生成文字，也能生成结构化的工具请求，例如“请调用 `files__read`，文件编号为 F”。

`files__read` 中，`files` 是服务名，`read` 是动作名，两个下划线是 Reasoner 对模型展示工具名的约定。**Reasoner** 是 SUMP 组织模型调用、工具派发与结果处理的服务。

这一过程分成四步：

1. SUMP 服务声明自己提供什么动作，Reasoner 从服务名册组织模型可见的工具目录。
2. 模型生成工具名和参数；此时还没有证明文件已读取。
3. Reasoner 解析参数、检查工具是否在目录里，再向目标服务发出 SUMP 请求。
4. 目标服务返回数据或错误，Reasoner 把它放回工作上下文，模型才有依据继续回答。

“工具调用”在模型 API 中首先是一份请求数据。执行权限、输入检查、网络故障和实际业务仍由软件实现承担。

源码入口：[rosterTools、argsToRaw、runToolCall](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/reasoner/server/infer.go)。

## 3. 有好几种编号，因为它们回答的问题不同

| 名字 | 白话含义 | 用来回答什么 |
|---|---|---|
| `conversation_id` | 对话窗口的编号 | 这属于哪段会话？ |
| `task_id` | 一件有始有终工作的编号 | 这是整理文件，还是下一件新工作？ |
| 信封 `id` | 一次协议请求的编号 | 这条响应在回答哪条请求？ |
| `trace` | 一条调用链的追踪编号 | 哪些服务消息沿着同一条链发生？ |
| 模型工具 `call.ID` | 模型本轮提出的某个工具请求编号 | 这份工具结果应对应哪次模型调用？ |
| `item_id` | 目标服务受理异步工作后给出的句柄 | 后续进度说的是哪项后台工作？ |
| `boss` | 业务交付目标 | 最后应把内容交给哪个入口服务？ |

**句柄**就是“以后拿着它再找这项工作”的标识，不是操作系统窗口，也不天然是密码。

一个会话可以先后有多个任务。当前 memory 用数据库约束保持同一会话最多一个 `active` 任务；多个后台工作可以仍在进行，因此“当前任务结束”与“全部后台活动结束”并不相同。

这些编号用于关联。`from` 写成某个服务名，只说明消息声称的来源；当前 SUMP 原生信封并不因此自动获得密码学认证。

## 4. 黑板：正在工作的临时记录本

Reasoner 的 **黑板** 是一个会话当前工作的内存状态。它记下模型已经看过什么、工具还有哪些没返回、当前是否正在生成回答。

| 字段 | 可以怎样理解 |
|---|---|
| `messages` | 给模型看的当前消息链 |
| `pending` | 普通工具请求尚未返回的名单 |
| `gen` | 内容变化次数，类似记录本的版本号 |
| `seen` | 已经交给某轮模型阅读的版本号 |
| `running` | 当前是否有一轮模型正在运行 |
| `closed` | 这份工作状态是否已经关闭 |
| `taskID` | 对应 memory 中哪份任务档案 |

假设模型正在读第 4 版记录本，工具结果让记录本变成第 5 版。`gen != seen` 能表达“模型还没看到新内容”，避免直接用旧结论结束任务。

同一会话通常由 `running` 保证同一时刻只有一轮模型推进；工具则可以在后台分别执行。这里的并发能力不等于让同一个模型请求凭空拆成几十个独立大脑。

黑板在内存里，程序重启会丢失；memory 保存的历史与任务档案是另一层。持久历史并不自动恢复所有在途请求。

源码入口：[taskState、boardOpen、boardKick、tryClose](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/reasoner/server/board.go)。

## 5. 两层异步，先不要混在一起

**同步**表示这次请求等到结果再返回；**异步**表示先受理，实际结果稍后再给。它们描述一段交互关系。

第一层是 Reasoner 后台发普通工具请求。例如文件读取本身一次返回全文，Reasoner 仍可同时等待另一个文件请求。未返回者登记在 `pending`，模型收尾时需要考虑它们。

第二层是工具声明 `Async:true`。例如计时器先返回 `item_id`，等计时结束，再主动向调用方发送 `report_result`。

下面是**简化业务正文示意，并非可直接发送的完整 SUMP 信封**：

```json
{"item_id":"timer-example-1","phase":"accepted"}
```

稍后的补报示意：

```json
{"item_id":"timer-example-1","phase":"done","text":"计时结束","final":true}
```

`accepted` 表示受理；具体阶段名称由服务定义，不能要求所有服务第一次都叫 accepted。`final:true` 表示这项工作不再预期普通进度更新，**不表示一定成功**，最终结果也可能是失败或取消。

`unknown` 则是“目前无法确定远端实际结果”。网络等待超时后，远端可能已经执行，不能立即按“未执行”重试。不同模块表达 unknown 的字段和错误不同，它不是全项目统一的一张状态表。

普通请求收到异步回执后可以离开 `pending`，但 Reasoner 会另外保留该异步工作的登记。内置 `wait` 等待普通 pending，并披露未结束的异步项；它不把所有长任务都阻塞到最终完成。

## 6. 结果为什么可能比回执先到

别把网络想成一条严格排队的传送带。回执和补报可以走不同连接：工具极快完成时，补报可能先到。

这一版代码先做 `beginAsync`，登记“我即将向这个服务发请求”；随后才发送网络调用。回执到来后，`finishAsync` 再把服务给出的 `item_id` 绑定到原始工作。

```text
派发前预留 → 请求送出 → 早到补报暂存 → 回执建立句柄 → 精确取出暂存补报
```

最终关联键是 **来源服务 + trace + item_id**。只有处于待回执窗口的相应来源和链路，才允许暂存未知句柄的早到消息；不是收下任何陌生补报。

暂存有条数、字节数及每句柄条数限制。当前已受理与待回执登记合计最多 512，早到报告总数最多 128。有限容量用来避免无限占内存，不是吞吐量承诺。

终态处理还会记短期“已完成标记”，用于忽略重复补报。这个标记也会过期，重启不保留；因此系统没有承诺永久的“恰好执行一次”。

源码入口：[beginAsync、finishAsync、actionReportResult、deliverAsyncLocked](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/reasoner/server/async.go)。

## 7. 一次完整模拟：两项计时，后来的先完成

**以下是根据代码约定的模拟，不是本篇实测记录；时间只用于说明顺序。**

1. 用户在会话 C 的任务 T 中请求两个计时：A 需要 8 秒，B 需要 3 秒。
2. 模型提出两份调用，Reasoner 分别预留登记、发出请求。
3. 目标服务返回两个不同 `item_id`。用户可以先看到“已受理”。
4. B 先完成。Reasoner 按来源、trace、item_id 找回 B，不会因为它第二个发出就要求第二个返回。
5. 若用户仍在同一任务，B 的结果进入原黑板；A 继续由目标服务计时。
6. 如果用户已经切换到新任务 T2，A 后到的结果保留 T 的归属，直接交付原任务，不塞入 T2 的模型上下文。
7. A 的同一终态再次到达时，短期完成标记阻止重复投递。

“按来源关联正确”仍依赖可信的原生网络边界；它不能代替对网络对端的认证。

## 8. Context、取消与人的暂停分别是什么

Go 的 **Context** 是给一项工作传递超时、取消等信号的对象。函数可以检查它，决定停止等待；它不是模型的文字上下文。

**goroutine** 是 Go 启动一段可并发推进工作的方式。启动它以后仍须考虑谁取消它、什么时候回收它、它占用多少资源。

`user_hold` 是用户操作发给 Reasoner 的控制信息。它阻止新一轮推理和新工具派发，不等于强制终止所有已经发出的操作。

- `primary`：保持停手，等待用户下一条消息或明确解除。
- `secondary`：部分停手，其他非常驻异步工作结束时可自动恢复推进。
- `none`：没有停手，或明确解除已有停手。

**resident** 是常驻任务分类，例如长期监听。等其他工作结束时不应无限等待常驻项。尚未拿到回执、还不知道分类的请求不能被提前假定为常驻。

源码入口：[heldFor、hasExecutableAsync、releaseHold](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/reasoner/server/hold.go)。工具自己的停止机制另见 [第 06 课：批处理与并发边界](06-批处理与并发边界.md)。

## 11. 本版的边界与下一课

当前工具结果和补报会以带来源说明的文字加入模型消息链；标签有助于理解来源，**并未证明已经防住提示词或工具内容注入**。模型输出 `task_status=done` 也只是任务判断，不是测试报告。

本篇只静态核查当前行为。早到消息丢弃、未知结果、服务重启和投递失败仍需按具体路径验收。下一篇读 [SQLite、记忆与向量检索](05-SQLite记忆与向量检索.md)，理解离开临时黑板后，哪些资料真正留了下来。
