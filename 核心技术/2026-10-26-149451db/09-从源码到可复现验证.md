## 1. 先固定版本

本课程基于主线提交 `149451dbf9ec953006da7c1926c336cfd9da0633`。不要用一个不断变化的 main 下载包，去复现几个月前的结论。

不熟悉 Git 时，可以用浏览器下载 [这一提交的源码 ZIP](https://github.com/NouSart/sump/archive/149451dbf9ec953006da7c1926c336cfd9da0633.zip)。解压到新建的学习目录，避免覆盖正在使用的系统和数据。课程也保存了 [只含公开源码的快照](https://github.com/NouSart/sump/archive/149451dbf9ec953006da7c1926c336cfd9da0633.zip)。

解压后，找到同时有 `go.work`、`README.md`、`protocol`、`reasoner` 等项目的那层文件夹。这才是下面说的“项目根目录”，不是 ZIP 文件所在目录。

**根目录**是本项目这一棵文件树的起点。路径错一层时，同样的命令会找不到模块。

## 2. 工具分别为了什么

| 工具 | 在哪一类操作需要 | 当前项目依据 |
| --- | --- | --- |
| Go 1.26 系列或满足 go.work 的工具链 | Go 服务测试与构建 | `go.work` 声明 1.26.0 |
| Node.js 与 npm | 网页构建和前端测试 | CI 使用 Node 24；可优先对齐 |
| Python | embedding 服务与包含它的联调 | 具体依赖见 `embedding/pyproject.toml` |
| PowerShell / pwsh | Windows 操作与 PowerShell 命令解析相关测试 | 系统 Windows PowerShell 与额外安装的 pwsh 不是同一个程序 |
| 编辑器 | 阅读文件、搜索函数、保存代码 | 可使用已经安装的编辑器 |

安装步骤沿用 [准备 Windows 开发环境](../../基础课程/00-准备Windows开发环境.md)。本次不自动下载安装或更改全局执行策略。先确认你已有的版本，不要为了每个练习重装一套环境。

### 怎样打开正确的命令窗口

在文件资源管理器进入项目根目录，右键空白处，选择“在终端中打开”。窗口提示符左边显示当前目录。这里只是让命令在正确位置执行，不要求你理解全部 PowerShell 语法。

下面命令每次只复制一行，不要复制代码块标记，也不要复制文档中的解释。

```powershell
go version
```

预期输出包含 `go version` 和版本号。若提示找不到 go，先处理环境定位；这不是 SUMP 业务功能失败。

## 3. 第一项实际练习：消息层测试

在根目录运行：

```powershell
go -C protocol test ./... -count=1
```

逐段解释：`go` 调用 Go 工具；`-C protocol` 临时在 protocol 目录工作；`test` 执行测试；`./...` 包括该目录下面的包；`-count=1` 要求本次实际执行而不是复用先前测试结果。

首次运行可能下载 Go 模块依赖，需要网络。它不是在调用真实模型，也不需要模型密钥。测试可能创建临时目录、在本地监听临时端口；这些属于测试运行，不等于上线服务。

预期最后看到 `ok` 或明确失败。不要求秒数、缓存日志和测试输出与你的机器完全一致。

随后可以只运行一个消息大小限制测试：

```powershell
go -C protocol test . -run '^TestClientMaxMessageBytes$' -v -count=1
```

`-run` 选择测试名字；`-v` 显示详细结果。这个测试名已在固定源码中核对。若名称打错，可能出现“没有匹配测试”，不能把这种情况算成验证通过。

## 4. 第二项练习：MCP 的双向真实进程测试

先运行 MCP 单元测试，再运行集成用例：

```powershell
go -C mcp test ./... -count=1
```

```powershell
go -C tests test . -run '^TestMCP(Bidirectional|RemoteTLSPreparation)$' -v -count=1 -timeout 180s
```

第二条会构建并启动实际服务进程，配合受控的外部测试服务，验证翻译和 TLS。它不需要你的真实模型或公网设备。测试自建的证书与临时目录不能拿来当生产环境配置。

如果出现 Windows 网络权限弹窗，先确认它对应正在测试的程序和本地范围；不需要为了测试关闭防火墙或关闭证书检查。不确定时保留错误信息再排查。

**真实进程**意味着真的运行了程序；**测试服务**意味着对方行为是人为控制的。两者可以同时成立，不要误称“已经兼容所有第三方客户端”。

## 5. 前端可以先做构建与组件测试

进入 `frontend` 目录：

```powershell
cd frontend
```

依次运行：

```powershell
npm ci
```

```powershell
npm run build
```

```powershell
npm test
```

`npm ci` 按锁文件安装依赖，会访问包源并重建当前学习副本的 node_modules。`build` 做类型检查和构建。`test` 包含服务端测试与网页组件测试。

组件测试使用模拟的浏览器环境。通过它不代表已在真实浏览器里完成全部操作。因此，构建、组件测试和页面手工验收是三个层次。

测试完成，输入 `cd ..` 返回项目根目录。完整启动方式看这个版本的 `README.md` 与 `scripts/run-local.ps1`，而不是套用旧审批演示脚本的端口。

## 6. 怎样读懂结果

| 输出或状态 | 你可以说什么 | 不能说什么 |
| --- | --- | --- |
| build 成功 | 源码和依赖能构建 | 功能全部正确 |
| 某用例 PASS | 该用例在这次环境通过 | 未覆盖场景也通过 |
| SKIP | 条件不满足，未执行该用例 | 用例通过 |
| 真进程联调通过 | 写明的服务链可工作 | 真实第三方、公网都兼容 |
| CI 成功 | 该提交、该工作流中的任务成功 | 包括所有被跳过的测试 |
| 页面看到最终输出 | 展示链完成了这次观察 | 业务副作用一定符合预期 |

当前 `TestLiveDeepSeek` 同时检查显式启用开关和密钥。常规离线验证不要求打开它；模型请求可能产生费用，因此不能把无密钥导致的跳过改成伪造通过。

源码：[真实模型测试门槛](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/reasoner/tests/live_test.go)、[CI 工作流](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/.github/workflows/ci.yml)。

## 7. 为什么 CI 在 Linux 跑，项目仍可在 Windows 开发

**CI** 是 Continuous Integration，即提交后自动检查。GitHub 借一台临时机器运行工作流，不会把你的 Windows 自动改成 Linux。

Go 很多部分能跨平台运行，但进程终止、路径和 shell 语义可能不同。Windows 本地验证与 Linux CI 是互相补充，不能互相冒充。`-race` 是帮助发现共享内存竞态的工具，不是所有并发问题的证明器。

## 8. 记录一次能复现的结果

在项目外写一页记录即可：

```text
源码提交：完整哈希
系统与工具版本：实际版本
工作目录：学习副本根目录
执行命令：原样记录，不含凭据
结果：通过 / 失败 / 跳过
覆盖：这次检查了哪条链
未覆盖：没有执行的场景
```

公开提交只放必要测试代码、说明和匿名化结论。个人路径、密钥、完整用户内容和临时运行故事不应进入项目仓库。

## 9. 常见故障从近到远排查

1. 找不到命令：确认工具已安装且当前窗口能找到。
2. 找不到模块：确认当前目录和 `go.work`。
3. 下载依赖失败：查看网络与源，不先改业务代码。
4. 端口占用：确认是谁占用，不按名称批量结束所有同名程序。
5. 测试失败：保留首个失败断言及对应提交，不只截最后一行。
6. 请求超时：检查是否已经派发；有副作用的请求不能靠不断重试证明“终于成功”。
