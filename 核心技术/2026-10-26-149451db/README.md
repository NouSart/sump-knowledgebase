## 今天只学一件事

先回答：“SUMP 为什么要拆成多个服务？”

答案不是为了把一个程序切得越碎越好，而是让能力有自己的负责人、运行过程和数据边界。每个服务只承诺自己的输入输出。别人可以替换它，也可以通过明确的消息调用它，不必知道它内部如何存数据。

这与“简洁、可组合、自定义强”的方向一致。需要一个小助手时可以只启用必要能力；不是一开始就建设插件商店、发行版平台或统一管理所有任务的巨型服务。

## 一张总图

```mermaid
flowchart LR
    U[用户] --> F[frontend 网页门户 / qq]
    F --> R[reasoner 推进任务]
    R <--> M[memory 记忆]
    M --> E[embedding 生成向量]
    R --> B[batch 批量调用]
    R --> T[timer / files / images]
    R --> S[shell 执行命令]
    S --> A[approval 命令裁决]
    A --> F
    R --> C[mcp 双向翻译]
    C <--> X[外部 MCP 应用或工具]
    Z[settings-center 名册与设置] -.地址与配置.-> R
    Z -.地址与配置.-> C
```

箭头表示调用或交付关系，不表示所有能力都能绕过权限直接调用。省略了多数注册线，避免把图画成线团。`protocol` 和 `service` 是共享代码库，不另画成运行服务。
