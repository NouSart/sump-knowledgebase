## 1. 学习目标

- 分清并发、并行、批处理和工具受理回执。
- 看懂批次中的单项状态，与整个批次状态的区别。
- 理解暂停、取消、失败即停为什么不等于杀死所有远端程序。
- 知道容量上限、重启恢复与结果不确定之间的联系。

把一次批次想成一张清单：“把这 20 份已确定输入交给同一种动作处理。”它省去了模型逐项重复发指令的过程，但没有替模型决定清单应该是什么。

## 2. 并发、并行和批处理，各是什么

**并发**：同一段时间内推进多个工作。例如 A 等网络时，程序可以发送 B 的请求。

**并行**：多个工作在某一时刻真正同时执行。例如两颗 CPU 核心分别计算。并发程序可能获得并行效果，但还取决于机器与目标服务资源。

**批处理**：把一批输入连同并发度、失败策略一次提交。批处理也能设为并发度 1，因此“批量”和“并行”不是同义词。

| 场景 | 可以怎样理解 |
|---|---|
| 依次读取两个独立文件 | 串行推进，第二个等待第一个 |
| 同时发出两个独立读取请求 | 并发；实际读盘仍受存储限制 |
| 提交 20 项、并发度 4 | 一批最多四项处于调用中，其余是本批未开始项 |
| 第二步必须使用第一步的输出 | 有依赖，不能仅靠增大并发度消除等待 |

SUMP 的服务解耦让不同能力独立推进；它没有改变依赖关系，也没有保证“请求多十倍，耗时少十倍”。

## 3. batch 是独立服务，不是全局指挥中心

`batch` 管理一次已经明确声明的批次：接收项目清单、限制并发、调用目标、保存简要进度并补报。

Reasoner 决定要做哪些工作；目标服务执行自己的业务；batch 只管理这份清单。MCP 则翻译内外协议，不接管 batch 的工作计划。

一批输入使用同一个 `service` 与 `action`。每项的 `input` 可以不同，`tag` 是方便阅读的标签，`key` 表示是否为关键项。

下面是**给 batch.run 的业务正文教学示例**。`worker.slow` 是测试替身的动作，正式项目没有因此自动多出这个服务；它也不是可直接粘贴到网页聊天里的完整协议消息。

```json
{
  "service": "worker",
  "action": "slow",
  "items": [
    {"input": {"ms": 100}, "tag": "A", "key": true},
    {"input": {"ms": 300}, "tag": "B"},
    {"input": {"ms": 200}, "tag": "C"}
  ],
  "concurrency": 2,
  "on_error": "continue",
  "wake": {"mode": "key"}
}
```

输出首先是批次 `item_id`、总项数、受理阶段和任务分类。稍后 `report_result` 送进度或终态；需要明细时使用 `status`、`result` 等动作。

源码入口：[actionRun 与 runningJob](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/batch/server/run.go)、[查询动作](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/batch/server/query.go)。

## 4. Batchable 是明确加入，不是“发现就能批量”

服务在能力声明中设置 `Batchable:true`，表示允许 batch 调用该动作。未声明时，batch 返回 `BATCH_NOT_BATCHABLE`。

**能力声明**是服务告诉别人的接口说明；**准入**是接受工作前判断它能否进入当前流程。这里只通过目录标记做准入，标记本身不构成对公网调用者的认证。

batch 还拒绝把自己作为批量目标，返回 `BATCH_NESTED`。这防止“一个批次再套十个批次”的层层放大；当前不是任意深度的工作流引擎。

目标没有注册与目标动作不允许批量是两类不同问题。看见前者先检查服务发现；看见后者要审查该动作是否适合批处理，不能为了让报错消失就随手把标记全改成 true。

尤其注意：batch 的单项完成以目标这次 `Call` 的返回为边界。若动作只返回“已受理”，不能未经设计就把它当成业务完成；异步动作是否 Batchable 必须由对应服务契约明确决定。

## 5. 容量上限：忙不过来时明确拒绝

本版构造函数默认值如下，运行时设置可能覆盖它们：

| 设置 | 默认 | 解释 |
|---|---:|---|
| 单批默认并发度 | 8 | 调用方没有指定时采用 |
| 单批最大并发度 | 64 | 一份清单允许申请的并发上限 |
| 全局在途额度 | 64 | batch 实例跨批次的预留容量 |
| 单批最大项数 | 1000 | 一次最多接纳多少明确输入 |
| 单项默认超时 | 1 分钟 | 等待目标一次调用的时间限制 |
| 输出预览预算 | 2048 字节 | 每项结果只保留有限摘要 |

**在途**指请求已经发出、尚未得到本次调用结果。**槽位**是用来记账的容量单位，不是实际 CPU 核心。

受理阶段会先预留该批所需容量，再落库并启动工作。容量不足明确拒绝，不无限等待新批次。单批尚未开始的项目仍可等待本批槽位，这是有限清单内部的等待。

Reasoner 的工具请求并发、batch 容量、shell 实际进程数和 MCP 入站限制是不同层。一个服务快速返回异步回执后，上层请求槽可能释放，目标实际工作还在运行；因此目标服务自己的限制仍有必要。

源码入口：[默认设置与容量配置](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/batch/server/server.go)。

## 6. 实现骨架：工人、锁和等待汇合

`runScheduler` 启动有限数量的 **worker**。worker 可以理解为负责领取并处理一项工作的执行单元，这里使用 Go 的 goroutine。

**信号量**是限制同时进入数量的机制；代码用有容量的 channel 实现。占一个位置才能领活，结束后归还。

**互斥锁**保证一段共享状态同一时刻只由一条执行路径修改。它防止两名 worker 都认为自己领到了同一项，或暂停与领活互相覆盖。

**WaitGroup** 是等待一组 goroutine 收尾的计数器。调度器不能只看“待领取清单空了”，还要等已经派出的项真正返回。

这些都是协调机制，不会自动消除所有竞态。**竞态**是结果取决于两个并发操作恰巧发生的先后，相关用例需要专门安排时序来验证。

源码入口：[runScheduler、claim、runItem](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/batch/server/run.go)。

## 7. 单项状态与批次状态分开看

| 单项状态 | 含义 |
|---|---|
| pending | 这项尚未开始 |
| running | 这项请求已经派发 |
| ok | 本次目标调用成功返回 |
| failed | 这项调用失败或被记录为结果未知 |
| skipped | 这项尚未执行就被取消或策略跳过 |

整个批次另有 accepted、running、paused、done、failed、cancelled 等阶段。批次 paused 时，已有项仍可能 running，不能只看顶层文字就认为所有副作用都停止了。

`wake.mode=all` 通常等收尾汇总；`wake.mode=key` 在关键项都结束时可以先发一次非终态进展，剩余项结束后再发终态。首次失败也可以触发进展通知。

关键项“结束”并不保证每项成功。应一起看成功、失败、跳过和未完成计数；不能只见“关键项已完成”就宣称业务目标达成。

## 8. 暂停、恢复、取消和失败即停

| 操作 | 未开始项 | 已派发项 | 能否恢复 |
|---|---|---|---|
| pause | 保持 pending，暂不再领取 | 等它们返回 | 可以 resume |
| resume | 继续领取，需要重新有容量 | 不应重复已完成项 | 这是恢复操作 |
| cancel | 转 skipped | 等它们返回，不在此强杀远端 | 不作为暂停恢复 |
| on_error=stop | 首次失败后停止派发，剩余转 skipped | 已派发项仍收尾 | 不自动重跑失败项 |

**幂等**表示重复操作不会重复产生额外效果。例如对已结束批次重复控制，当前接口可以返回 `affected=0`；这不等于任意业务工具也具有幂等性。

暂停后，要等实际在途项排空再释放容量；过早释放会让更多工作进入，突破真实限制。恢复拿不到容量时，任务仍暂停，并应有明确忙碌反馈。

Reasoner 的 `user_hold` 另行阻止继续思考和派新工具。batch.control 只控制批次，执行端负责停止实际子进程；不能用其中一层替代所有层。

源码入口：[actionControl 与 controlMemory](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/batch/server/control.go)。

## 9. 一次模拟：四项工作中途取消

**以下仅为状态模拟，不是实测耗时。** A、B、C、D 四项，并发度为 2：

1. 批次先把总单与四项一起写入数据库，给调用方返回 item_id。
2. A 与 B 开始，C 与 D 留在本批待开始清单。
3. 用户发 cancel。调度器不再领取 C、D，最终把它们记为 skipped。
4. A、B 已经交给目标服务，仍等待各自结果；取消不会倒转它们已经造成的影响。
5. 两项返回后，批次落 cancelled 终态并发送汇总。
6. 汇总中应有四项的完整去向，例如成功 2、失败 0、跳过 2。

真实情况下，取消到达前 C 可能刚好已被领取，因此不能死记“取消必定成功 2 项”。应该验证总数一致，以及取消后没有继续领取未开始项。

## 10. 落盘与重启：记住状态，不等于重放一切

**持久化**是把数据写进可跨进程重启保留的存储。batch 使用自己的 SQLite 账本，保存总单、各项状态和未完成项输入。

`CreateJob` 用数据库事务写入批次与子项；已结束项会清理原始输入并保留有限结果预览。这是数据保留规则，不能当作加密或完整审计保证。

重启时，当时 running 的项会标为失败，并注明“执行结果未知”；因为它可能已经在外部完成，代码不擅自再执行一次。尚未开始项默认转入暂停批次，用户恢复后继续；设置 `resume_on_start` 时可尝试自动恢复剩余项。

恢复还要保留原来的并发、超时、失败策略和唤醒模式，不能变成一份意思不同的清单。容量不足时仍可能保持暂停。

源码入口：[CreateJob、MarkInterrupted](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/batch/store/store.go)、[recoverAfterRestart、rebuildJob](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/batch/server/server.go)。

## 11. 从零阅读与可选测试

**先做纯阅读：**打开 [批处理测试](https://github.com/NouSart/sump/blob/149451dbf9ec953006da7c1926c336cfd9da0633/batch/tests/service_test.go)，查找 `TestCancelSkipsUnstarted`。写出它检查的三个事实：在途项完成、未开始项跳过、各项数量加起来等于总数。

再看 `TestPauseResumesWithoutRerun`，找目标被调用次数的断言。**断言**就是“这个条件不成立，测试就失败”的规则；没有断言的日志不能证明没有重复执行。

若要运行，先完成 [Windows 环境准备](../../基础课程/00-准备Windows开发环境.md)，在完整源码的 `batch` 目录打开编辑器终端：

```powershell
go test ./tests -run '^(TestCancelSkipsUnstarted|TestPauseResumesWithoutRerun|TestNotBatchableRejected|TestRestartTurnsRunningIntoPaused)$' -count=1 -v
```

**预期：**这四项各显示 PASS。测试使用本机回环网络和受控 worker，不需要模型 API，不执行真实 shell。首次运行可能下载依赖，测试会使用临时数据库和临时端口。

如果端口监听被环境拒绝，先区分环境限制与断言失败；若提示 `no tests to run`，核对目录和源码版本。任何失败都保留测试名称与完整错误，不自行改成“通过”。

## 12. 本版还不能据此承诺什么

“默认 64”是容量配置，不是实际测出的吞吐量；“控制接口已存在”也不证明所有暂停恢复竞态都已覆盖。尤其暂停尚未排空就立刻恢复时，除了检查剩余项目继续完成，还应检查全局预留额度最终归还，避免只验证业务结果而漏掉容量记账。

本文未运行压力或竞态检查，也没有验证任意外部服务的取消行为。保持这些边界清楚，才能把“程序里有实现”“测试里有断言”“当前环境实际通过”三件事分别记录。
