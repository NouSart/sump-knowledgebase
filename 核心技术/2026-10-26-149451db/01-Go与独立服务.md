## 1. 这一章学会什么

读完后，你应能回答三个问题：`service/` 为什么不是要启动的服务器；一个请求为什么不会挡住其他请求；怎样从源码找到一个服务的入口。

不必先记住所有英文。先记一句：**代码的分组方式，与运行时有几个程序，是两件事。**

## 2. 从一条街上的工作室开始

想象一条街上有记忆工作室、文件工作室和计时工作室。每家有自己的员工、工具和记录本。

大家都用同款信封和登记表，但卖信封的说明书不是一家正在营业的工作室。

| 生活里的东西 | 在 SUMP 中是什么 | 怎样找到它 |
|---|---|---|
| 一家正在营业的工作室 | 进程：一个运行中的程序实例 | 启动后的 `timer.exe` 等 |
| 一整套制作图纸 | Go 模块：一起管理依赖的一组代码 | 有 `go.mod` 的目录 |
| 图纸中的一组相关零件 | Go 包：同一目录中可共同使用的代码 | 文件开头的 `package` |
| 统一信封格式 | `protocol` 库 | `protocol/envelope.go` |
| 通用开店流程 | `service` 库 | `service/service.go` |
| 开店入口 | `main` 函数 | 例如 `timer/main.go` |

**库**就是供其他程序调用的代码。`protocol` 和 `service` 不需要各自启动一个进程；使用它们的服务把所需代码编进自己的程序。

`timer/server` 虽然叫 server，它首先是一个包。是不是独立进程，要看有没有把它作为程序启动，不能只看名字。

## 3. Go 在项目里做什么

Go 是一种编程语言。SUMP 用它编写大部分服务、消息协议和通信骨架。

**编译**是把人能读的源码加工为操作系统能运行的程序。Windows 上的输出通常是 `.exe`。编译成功只说明代码通过了这一步检查，不代表网络或业务已经正确。

SUMP 不是“只能用 Go”。前端和 embedding 使用其他技术；只要双方理解同一消息协议，不同语言也能通信。

本版 `go.work` 声明 `go 1.26.0`。这是源码工作区的要求，不是说每台读者电脑已经安装了该版本。

### 三个容易认错的文件

| 文件 | 白话解释 | 它不负责什么 |
|---|---|---|
| `go.mod` | 本模块的名称、Go 要求和依赖清单 | 不记录每次运行结果 |
| `go.sum` | 下载依赖的内容校验记录 | 不是“所有依赖已经安全”的证明 |
| `go.work` | 告诉 Go 本机哪些模块一起开发 | 不负责启动各个服务 |

**依赖**是借用的代码。`service/go.mod` 引用 `protocol`，并用 `replace ... => ../protocol` 指向旁边的本地目录。

所以只把 `service/` 单独复制走，可能会缺少 `../protocol`。独立服务指运行和职责独立，不代表源码可以任意删去依赖后继续构建。

## 4. 真实入口：timer 怎样启动

打开 `timer/main.go`，按下面的顺序读。不要从每个符号开始背语法。

1. `flag.String` 等声明启动参数，例如名字、监听地址和设置中心地址。
2. `flag.Parse()` 读取启动时给出的参数。
3. `server.New(...)` 创建计时器对象，并把引导配置交给它。
4. `s.Start(context.Background())` 开始监听并向设置中心注册。
5. 主函数等待退出信号。
6. 收到退出信号后停止计时，再关闭服务。

**参数**就是这次启动填的选项。例如 `-addr` 决定在哪个网络地址接收请求。它不是用户让计时器等待几秒的业务参数。

`timer/server/server.go` 再调用 `service.New(...)`，描述服务名片，注册 `sleep`、`cancel`、`list` 的处理函数。

下面两行直接取自本版的动作注册，是真实存在的代码：

```go
s.Handle("sleep", s.actionSleep)
s.Handle("cancel", s.actionCancel)
```

`Handle` 的意思是“以后有人请求这个动作，就交给这个函数”。**函数**是一段有名字、能被调用的代码。

名片里写 `Provides` 是“告诉别人我提供什么”；`Handle` 是“真正接到请求时怎么做”。两边都要正确，不能只写名片就当功能完成。

## 5. goroutine：多个工作怎样同时推进

想象工作室接到一份要等十分钟的委托。员工不必站在门口等十分钟，可以登记任务，让门口继续接客。

Go 中的 **goroutine** 是可并发推进的一段执行流程。常见写法是 `go 某个函数()`。

在 `service/service.go`，读到一个请求后会执行：

```go
go s.handleJump(c, env)
```

这样读取连接的流程可以继续接收消息。处理慢请求不会直接让这个读循环一直等着它返回。

**并发**是多件事在同一段时间推进；**并行**是它们在某个时刻真正同时计算。一个 CPU 核心也能交替推进很多等待网络的任务。

这行代码没有自动给任务数量加上限。实际容量控制仍需业务服务自己实现，例如 timer 的 `max_pending`。不能把“用了 goroutine”理解成“无限并发也安全”。

## 6. channel、锁和 Context 各管什么

它们不是三种相同的“并发加速器”。先认识各自职责。

| 名称 | 白话解释 | 实际代码里的用途 |
|---|---|---|
| `channel`，通道 | 程序内递交消息或信号的小管道 | `protocol.Client` 等待某个请求的响应 |
| `Mutex`，互斥锁 | 同一时间只让一方操作一份共享东西 | 防止两个发送流程同时写同一条 WS 连接 |
| `Context`，上下文 | 携带取消信号和截止时间的对象 | 调用方控制自己最长等多久 |
| `defer`，延后执行 | 在当前函数离开时做收尾 | 关闭连接、取消计时资源、解锁 |

通道是同一进程内的协调手段，不是 WebSocket。服务之间传消息走网络，不是直接把一个 Go channel 交给另一进程。

`protocol.Client` 用 `pending` 表把请求编号对应到各自的通道。回包先看编号，再把结果交给等这一包的人。

Context 也不是模型的“聊天上下文”。这里只讲 Go 的生命周期控制对象，里面的超时不会自动杀死任意代码。

例如 `service` 给处理函数设置默认 30 秒超时，但函数必须主动检查 Context 或调用支持取消的操作。一直不理会取消信号的函数，不会因为这行配置就被强行终止。

## 7. 模拟一次计时委托

**以下是按源码解释的教学模拟，不是本章实测。**编号和时间都为示意。

1. 调用方交给 timer 的输入是 `{"ms":3000,"note":"练习"}`，表示等 3000 毫秒，也就是 3 秒。
2. timer 检查输入是否合法、当前计时数量是否已满。
3. 合法时登记计时，立即返回含 `item_id`、`phase:"queued"`、`fire_at` 的回执。
4. 处理这次请求的函数返回了，但计时器仍在服务进程中等待到点。
5. 到点后，timer 向原调用方发送 `report_result` 补报。

**回执**像“订单已收下”，**补报**像“订单处理结果”。不能收到第 3 步就声称第 5 步已完成。

如果第 3 步之后关闭 timer 进程，这个版本不会把尚未到点的计时持久保存以便重启恢复。`timer/main.go` 的退出提示明确说明了这一点。

## 8. 动手练习：先认路，再构建一个库

### 练习 A：完全不用命令

1. 在源码根目录打开 `go.work`，找到 `./protocol`、`./service`、`./timer`。
2. 分别打开这三个目录中的 `go.mod`，比较第一行的 `module`。
3. 打开 `timer/main.go`，找到 `func main()`；再打开 `service/service.go`，找到 `package service`。
4. 用自己的话填空：“timer 是可运行的____；service 是被引用的____。”

**应有结果：**填“程序／服务”和“库”。你还能指出 timer 的入口在哪里。只看懂目录结构，也算完成这一小步。

### 练习 B：可选的构建练习

需要电脑已有符合仓库要求的 Go；没有安装时先跳过，不必为读本章改变系统设置。

在编辑器打开整份源码，在 `protocol` 文件夹的终端依次执行：

```text
go version
go build ./...
```

`./...` 表示当前目录及子目录中的 Go 包。**预期结果：**构建无报错；这是库，所以当前目录不应出现一个可双击的 `protocol.exe`。

首次构建可能下载缺少的依赖并写入 Go 缓存；它不启动 SUMP 服务，也不调用模型。

若提示找不到 `go`，是工具未就绪；若提示找不到相邻模块，是目录不完整；若提示网络下载失败，是依赖获取问题。这三种情况都不能直接判定业务代码有错。
